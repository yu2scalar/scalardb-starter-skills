# scalardb-review-exception-handling

> Status: **3.19.1.3 (2026-10-20 — new skill: read-only review of ScalarDB exception handling)**
> Targets ScalarDB **3.19.1** (Java Transaction API and ScalarDB SQL API, Spring Boot or plain Java). Skill 10 of 10 in the scalardb-starter-skills walk-through — run it on the project generated by `scalardb-generate-springboot-starter` or on any other Java application that uses ScalarDB.

## Overview

A **read-only** review. The skill reads the Java sources of an application that uses ScalarDB, compares its exception handling with the official guidance bundled in `references/`, and emits one report. It **never modifies files**: every finding carries a recommendation in prose only.

The basis for every rule is `references/60-error-codes.md` §2 — the per-exception tables "Official handling guidance — Java Transaction API" and "Official handling guidance — SQL API", and "Rollback: required or optional" — plus the anti-patterns in `references/70-design-decisions-and-antipatterns.md` and the API facts in `references/30-crud-api-and-limits.md`. Cite the file and section in every finding.

### What this skill does NOT do

- Fix code, generate patches, or run the application or tests
- Review 2PC / Global Transaction (`TwoPhaseCommitTransaction`, `join()`, `resume()`) handling — **deferred in this prototype**; if found, list it once as a notice ("2PC / global transaction code present — not reviewed")
- Review non-ScalarDB exceptions (reflection, JSON mapping, HTTP status design) — see "Out of scope"
- Judge performance, schema design, or configuration files (use `scalardb-validate-config` for configs)

## Phase 0 — collect the target

```
Q0. Which directory should be reviewed? (default: the current directory)
```

Collect `**/*.java` under it, skipping `build/`, `target/`, `.gradle/`, `out/`, and generated sources. If no file imports `com.scalar.db.`, report "no ScalarDB usage found" and stop.

## Phase 1 — build an inventory (read before judging)

Read every file that imports `com.scalar.db.` and every class those files call into for transaction work. Build a short inventory, keeping `file:line` for each item:

1. **Transaction units** — each method that starts a transaction (`DistributedTransactionManager.start*/begin*`, `SqlSession.begin()`, `sqlSessionFactory.createSqlSession()` + `begin()`) and where it commits, rolls back / aborts, and closes.
2. **Exception handlers** — every `catch` / helper that a transaction unit uses on failure (follow helper methods such as `handleTransactionException(...)`; follow `throw e` / rethrow paths to the caller).
3. **Retry mechanisms**:
   - Spring Framework built-in (`org.springframework.core.retry.RetryPolicy` / `RetryTemplate`): `includes(...)` / `excludes(...)`, `predicate(...)`. **This policy matches the thrown exception and its nested causes, and an exclusion wins over an inclusion. A `predicate(...)` is combined with `includes` / `excludes` as AND: an exception is retried only when the type filter accepts it and the predicate returns true** — so a predicate is the way to reject exceptions that cannot be told apart by class (for example ScalarDB Cluster auth failures, see R10). (Spring Framework 7.0.x behavior.)
   - Spring Retry (`org.springframework.retry`): `@Retryable(retryFor / noRetryFor / include / exclude)`, `SimpleRetryPolicy` exception maps, custom `RetryPolicy` / classifier. Check whether causes are traversed (for example `traverseCauses`); if they are not, a wrapped exception does not match the policy.
   - Hand-written loops: `for` / `while` around `begin()` … `commit()` with a catch-and-continue (the official example's shape).
4. **Wrapping** — where ScalarDB exceptions are wrapped in application exceptions (`RuntimeException` subclasses, `CustomException`, repository exceptions), and whether later code looks at the cause chain or only at the outermost exception.
5. **SQL statements** — primary-key `UPDATE` / `DELETE` executed through `SqlSession.execute(...)` and whether the result's update count is read.

Only judge after the inventory is complete: a handler that looks wrong in one method may be correct because a shared helper or the retry policy handles the case.

## Rule catalog

Severity: **Error** = data inconsistency, a lost or duplicated update, or a failure reported as success; **Warning** = a missing retry, a leaked transaction, lost diagnostic information, or results that differ between the APIs; **Info (notice)** = a deviation from the official guidance that is practically harmless today. Errors and Warnings are **findings**; Info items are **notices**, listed separately and not counted as findings.

| id | check | severity | basis |
|---|---|---|---|
| R1a | `UnknownTransactionStatusException` (Core `com.scalar.db.exception.transaction.*` or SQL `com.scalar.db.sql.exception.*`) is **retried** — automatically by a retry policy or loop, or by catching it and starting the transaction again. The commit may already have succeeded, so a retry can apply the change twice. Recommend: do not retry; find out whether it committed (for example an application status record written in the same transaction) and keep the operation idempotent | Error | 60 §2 (both tables: "Retry? No — first find out whether it committed"); 70 AP-22 correct alternative |
| R1b | `UnknownTransactionStatusException` is **rolled back** (`rollback()` / `abort()` on the transaction or session). The official example does not roll back, but the rollback itself is practically harmless (60 §2 "Rollback": after a failed `commit()` Consensus Commit has already aborted itself and `rollback()` writes nothing). Report it as a deviation from the official example. If the rollback is by transaction ID on the manager (`manager.rollback(txId)` / `abort(txId)`), say so explicitly: 60 §2 notes it may write ABORTED over a committed transaction that was already cleaned up | Warning | 60 §2 (both tables: "Roll back? No"; "Rollback: required or optional") |
| R2 | `UnsatisfiedConditionException` (a condition such as `updateIfExists` / `deleteIfExists` was not met) is retried | Error | 60 §2 Java table; 70 AP-22 |
| R3 | `TransactionNotFoundException` (Core or SQL; `DB-CORE-20031`) is excluded from retry or treated as a non-retryable user error | Warning | 60 §2 (Java and SQL tables: retry from the beginning); 70 AP-21; 30 §5.1 |
| R4 | A failure path leaves the transaction open: no `rollback()` / `abort()` (Java) or `sqlSession.rollback()` (SQL) after a failure other than `UnknownTransactionStatusException`, including when a shared handler is bypassed | Error | 60 §2 "Rollback: required or optional"; 70 AP-28 |
| R5 | A transient conflict (`CrudConflictException`, `CommitConflictException`, SQL `TransactionConflictException` / `TransactionRetryableException`) can never be retried: caught and rethrown as a non-retryable exception, or excluded from the policy | Warning | 60 §2 ("Yes, from the beginning") |
| R6 | An exception from a transaction unit is swallowed: caught without rethrow, error result, or meaningful handling — especially when success is returned to the caller | Error | 60 §2; 70 AP-28 |
| R7 | A rollback failure replaces or hides the original exception (for example `throw new RuntimeException(ex)` in the rollback `catch`, or an unguarded `rollback()` that throws before the original exception is rethrown). Officially a failed rollback needs no action: log it and keep the original exception | Warning | 60 §2 Java table (`RollbackException` / `AbortException`: "just log it") |
| R8 | A `Scanner` (`getScanner(...)`) is not closed (no try-with-resources) or is iterated with for-each without handling the wrapped exception the iterator throws | Warning | 30 §2.1; 60 §2 Rollback table (open scanners) |
| R9 | A retry policy includes a base type (`TransactionException`, `SqlException`, `Exception`) without excluding the exceptions that must not be retried (R1a / R2 / R10 types), or excludes ones that should be retried (R3 / R5). Report it as one row together with its consequence (see "One problem, one row") | Error (UTS or condition) / Warning (R3, R5) / Info (auth only, R10) | 60 §2; 70 AP-22 |
| R10 | Authentication / authorization failures are retried. SQL API: `AuthenticationException` / `AuthorizationException` are separate classes, so `excludes(...)` works. **Java API with the Cluster client: they arrive as a `CrudException` (a `TransactionException`) with `isAuthenticationError()` / `isAuthorizationError()` set — not as separate classes — so `excludes(...)` cannot express them.** A Core policy that includes `TransactionException` retries them unless a `predicate(...)` (or equivalent check in a loop) rejects exceptions whose cause chain has either flag. Flag this only when the app uses the Cluster client (`scalar.db.transaction_manager=cluster`) with auth enabled (`scalar.db.cluster.auth.enabled=true`), or when you cannot tell from the configuration — then say so. **This is a notice, not a finding:** the official examples do not single these out (the SQL example retries every `SqlException` with a limit), so retrying them only wastes attempts and adds noise — it does not corrupt data. Say in the finding that "do not retry" is a recommendation (auth / permission errors are non-transient), not official guidance | Info | 60 §2 Java table (authentication / authorization row: the flags are documented in the official ScalarDB Cluster API guide; "do not retry" is this reference's recommendation, not official), "Cluster client: gRPC error → exception", SQL table; 70 AP-29 |
| R12 | A primary-key SQL `UPDATE` / `DELETE` does not check the update count. The SQL API has no counterpart of `UnsatisfiedConditionException`: a missing row succeeds with count 0, so the caller sees success (and a Java-API twin of the same endpoint fails) | Warning | 60 §2 SQL ("There is no SQL counterpart of `UnsatisfiedConditionException`"); 70 AP-30 |
| R13 | The transaction ID logged or returned on failure is read only from the outermost exception although ScalarDB exceptions are wrapped elsewhere, so the ID is lost — important for unknown-status verification | Warning | 60 §2 (UnknownTransactionStatusException: verify whether it committed) |
| R14 | `SqlSession` is never closed (no `close()` / try-with-resources). The official SQL API guide says to close it; in 3.19.1 `close()` only marks the session closed | Info | 60 §2 SQL API ("Close the SqlSession when done"; official SQL API guide) |

### Do not flag (correct patterns — avoid false positives)

- No rollback after `UnknownTransactionStatusException`, and the exception is not retried (official behavior), including when the check walks the cause chain.
- A rollback after `UnsatisfiedConditionException` followed by no retry (the official example rolls back, then returns).
- Retrying the whole transaction (a new `begin()` / `start()` per attempt) with a bounded number of attempts.
- Wrapped exceptions handled through the cause chain, including Spring Framework built-in retry (it matches nested causes and exclusions win).
- SQL: skipping `rollback()` after `UnknownTransactionStatusException` **when the session is discarded** (a new `SqlSession` per attempt). Only when the same session is reused would the leftover transaction make the next `begin()` fail.
- SQL: calling `sqlSession.rollback()` after `UnknownTransactionStatusException` **when the session is reused afterwards** — there it is effectively required (60 §2 "Rollback", SQL row), so it is not an R1b finding.
- Read-only transactions that commit (or roll back) after reading.
- `RollbackException` caught and logged only.

### Out of scope (do not report as findings)

- Exceptions that are not ScalarDB's (reflection, mapping, validation of user input), HTTP status choices (for example 9100 → 400 vs 404), and log volume.

## Report format

Write three parts, in this order.

1. **Findings** — one table sorted Error → Warning, then by file:

```
| severity | rule | file:line | finding | recommendation | reference |
```

2. **Notices** — Info items in the same columns (or "none").
3. **Summary** — counts per severity, the transaction units and retry mechanisms reviewed, and two or three correct patterns you confirmed (so the reader knows what was checked). When there are no findings, say "no findings — exception handling is consistent with the ScalarDB 3.19.1 guidance".

Quote the code briefly when it helps (one or two lines). Keep recommendations to what to change, not full patches.

- **One problem, one row.** When a retry policy (R9) causes a consequence elsewhere (R1a, R2, R3, R5, R10), report it as **one** finding: put the policy line in `file:line`, name both rules in `rule` (for example `R9 / R1a`), and list the affected units inside the `finding` text. Do not add separate rows for each affected call site — the counts in the Summary must reflect distinct problems.
- **Verify every `file:line` before writing it.** Re-read the cited file at that line (or the range) and confirm it shows the code you describe. Never cite a line number from memory or from another file; if a file is shorter than the cited line, the citation is wrong.
